# 性能说明（为什么之前卡，怎么修的）

> v1.9.4 修。如果你用的是 v1.9.3 或更早，**强烈建议升级** —— 旧版一开面板会卡死几秒。

---

## 问题：开面板卡死几秒

用户反馈「节点卡顿严重」。我用真实数据规模（11097 标签 / 8000 角色）做了离线基准，
在 Node 里把面板 JS 真跑一遍，量每次交互**新建的 DOM 节点数**和**样式写入次数**：

| 操作 | 建 DOM | 写 style |
|---|---|---|
| **开面板（旧版）** | **110315** | **625184** |
| 点一个标签（旧版） | 115 | 113 |

十万个 DOM 节点 + 六十二万次样式写入，**全部同步执行**。浏览器要一次性完成
布局和样式计算，这就是「卡死几秒」的直接原因。

## 根因：`renderGrid` 漏了分页

`renderGrid()` 里本该 `list.slice(0, CARD_LIMIT)` 再建卡片，但那行在某次恢复文件时丢了 ——
循环变成 `for (const t of list)`，**遍历全部 11097 个标签**，每个标签建
1 个按钮 + 2 个 `span`。`CARD_LIMIT = 150` 的定义还在，`appendMoreHint()`
函数也还在，只有调用处没了。

这不是设计问题，是一次文件回退事故。

---

## 修了这些

### 1. 恢复 `renderGrid` 的分页（关键）

```js
const shown = list.slice(0, CARD_LIMIT);   // ← 补回来
for (const t of shown) { ... }
...
if (list.length > shown.length) appendMoreHint(list.length - shown.length);
```

未渲染的卡片数会显示在网格底部（「另有 N 张卡片未渲染 —— 用分组或搜索收窄」）。

### 2. `el()` 改成一次写 `cssText`

原来是 `Object.assign(node.style, styleObject)` —— 每个属性一次 setter。
10 万个节点 × 平均 5~6 个属性 = 几十万次 setter。

现在把样式对象拼成 `cssText` 一次性写入：

```js
// 旧：每个属性一次 setter
Object.assign(node.style, { padding: "5px 9px", borderRadius: "12px", ... });

// 新：一次赋值
node.style.cssText = "padding:5px 9px;border-radius:12px;...";
```

保留失败兜底（老浏览器不接受 `cssText` 时逐条写）。

### 3. 点标签只重画受影响的卡片

原来 `sync()` 里直接 `renderGrid()` —— 点一个标签要把当前分类的卡片全部拆掉重建。
现在：

- `renderGrid()` 把「标签键 → { 卡片元素, 标签信息 }」登记到 `tagCards`
- `paintTagCard(card, info)` 负责单张卡的选中态
- `select()` 返回**受影响的键**（自己 + 互斥组里被顶掉的）
- `sync(previewNow, touched)` 只重画这几个

只有分类切换、搜索这类场景才走整体重建。

### 4. 预览请求防抖 220ms

原来每点一个标签就 `POST /anima_nsfw/preview` 一次。连点 5 个标签 = 5 次请求，
每次都让后端重新合成提示词。现在防抖到 220ms，连点只发最后一次，
并且用序号丢弃过期响应（避免旧响应覆盖新结果）。

### 5. 「作品 → 角色」改成一次建好的索引

原来 `allWorks()` 对每个作品调一次 `workChars()`，每次 filter 全部 8000 角色：

```
140 个版权作品 + 337 个角色库作品 = ~477 次 × 8000 = 380 万次比较
```

而且在 `renderWorkList()` 里每次都会重跑。现在联网拿到角色库时**一次建好 Map**，
之后 O(1) 取；`allWorks()` 结果也缓存。

### 6. 延迟预取角色库

开面板时会立刻去拉 1.7 MB 的角色库（为了侧栏能算每个作品的角色数）。
现在推到 `requestIdleCallback`（老前端退回 `setTimeout` 400ms），
不再和标签库抢带宽和主线程。

### 7. 搜索输入防抖 160ms

原来每敲一个字符就把网格重建一遍。

## 效果

| 指标 | 修前 | 修后 | 倍数 |
|---|---|---|---|
| 开面板建 DOM | 110315 | **1981** | **56×** |
| 开面板写 style | 625184 | **2068** | **302×** |
| 点标签建 DOM | 115 | **3** | **38×** |
| 点标签写 style | 113 | **5** | **23×** |
| 连点 5 标签的预览请求 | 5 次 | **1 次** | 5× |
| 切「游戏/作品」分类 | 23 ms | **8~12 ms** | ~2× |

## 怎么自己验证

```bash
node tools/animansfw_perf.mjs
```

不需要启动 ComfyUI、不联网（fetch 全走桩）。把面板 JS 在 Node 的 DOM 桩里真跑一遍，
用真实数据量测每个操作的 DOM 节点数和样式写入次数。

**看两个数**：
- **建 DOM** —— 一次交互新建多少节点，开面板应保持在几千以内
- **写 style** —— 写了多少次样式，这个在真实浏览器里会累积成布局/样式重算

如果哪天 `开面板` 又变成五位数，就是分页或批量化又被改坏了。

另外三套功能测试也必须全绿：

```bash
node tools/animansfw_panel_smoke.mjs            # 现代前端
node tools/animansfw_panel_smoke.mjs --legacy   # 剥掉 addDOMWidget 等
node tools/animansfw_panel_smoke.mjs --oldfe    # 老前端契约（1.12.8）
```

## 如果你还觉得卡

先确认版本（面板右上角有版本号），然后按顺序排：

1. **`🖼 缩略图 关`** —— 角色立绘有 60~150 张网络图片，关掉后是纯文字，最省
2. **「游戏/作品」分类下点具体作品** —— 会渲染该作品的角色卡；角色特别多的作品
   （几百个）会触发懒加载分批
3. **搜索框输入** —— 已经防抖，但如果标签库特别大（比如你自己导入了很多），
   建议先用左侧分组收窄再搜
4. **F12 → Performance 录一段** —— 看是不是别的节点包在抢主线程

`node tools/animansfw_perf.mjs` 的结果可以直接发给我。

## 真浏览器实测（v1.9.4 之后）

Node 桩环境的数字能反映 DOM 规模和样式写入，但**真实的布局/绘制开销**只有在
浏览器里才算得准。用 headless Chrome + CDP 在真实 ComfyUI 页面里跑：

```bash
node tools/animansfw_browser_e2e.mjs
node tools/animansfw_browser_views.mjs
```

| 项目 | 实测 |
|---|---|
| 面板首屏（含两帧布局+绘制） | **118 ms** |
| 面板 DOM | 620 节点 / 215 按钮 |
| 点一个标签的帧耗时 | **47 ms** |
| 点标签前后 DOM | 621 → 621（局部重绘，没重建网格） |
| 控制台本包报错 | 0 |

各视图切换（脚本里含 400ms 固定等待）：

| 视图 | DOM 节点 | 卡片 | 图片 |
|---|---|---|---|
| 服装预设（518 套） | 1408 | 163 | 62 |
| 姿势参考（297 个） | 1241 | 163 | 150 |
| 角色（8000 个） | 1033 | 133 | 120 |
| 剧情（11 线 / 66 拍） | 305 | 16 | 9 |
| 我的 | 194 | 13 | 0 |

**注意**：`47ms` 这个数包含了 `requestAnimationFrame` 两帧的等待，所以它衡量的是
"点一下到画面稳定"的端到端感觉，不是纯 JS 执行时间。
